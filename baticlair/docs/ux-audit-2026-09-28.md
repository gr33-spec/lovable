## Doublons supprimés

| Doublon | Décision |
|---|---|
| « Importer un document », « Importer une offre », « Analyser mes factures » à l'accueil | Un seul geste : **+**. Le type de document est reconnu automatiquement (PD-016). Même logique partout ; depuis une fiche, le chantier est prérempli |
| Bascule « Par article / Par fournisseur » dans le détail | Supprimée : la liste par fournisseur existe déjà dans la comparaison |
| « Importez le PDF » + adresse de transfert + bouton d'import sur la fiche | Une phrase : **+** depuis la fiche, ou transfert de l'e-mail |
| « Négocier cette ligne » (comparaison et détail) | Conservé aux deux endroits **volontairement** : même écran, même brouillon, même logique |

## Décisions de conception issues de la confrontation

| Sujet | Développeur / architecte | Designer | Artisan | Décision |
|---|---|---|---|---|
| Ordre des chantiers | Tri par date de création = simple | Liste stable | « Celui d'hier doit être en haut » | Tri par **dernière activité** (`lastActivityAt`), mis à jour à chaque action métier |
| Portée de la recherche | Filtrer par statut | Respecter le filtre choisi | « Je cherche Dupont, même si c'est fini » | Une recherche porte sur **tous** les chantiers ; hors recherche, « En cours » par défaut |
| Mot « archivé » | Statut technique `archived` | — | « Un chantier est terminé, pas archivé » | Statut technique inchangé ; libellé **« Terminé »** |
| Bouton d'import | Un point d'entrée = une route | Bouton flottant central | Pouce, une main, sur le chantier | **+** central dans la barre, sur tous les écrans de navigation |
| Barre de navigation pendant une tâche | — | Concentration | « Je ne veux pas quitter par erreur » | Barre visible sur les écrans de consultation ; **masquée** pendant une tâche (questions, comparaison, envoi d'un message), qui se ferme par Retour ou ✕ |
| Double appui | Idempotence | Désactiver le bouton pendant l'envoi | « J'ai appuyé deux fois, ça en a créé deux » | Les deux : clé `Idempotency-Key` par action + bouton désactivé pendant l'envoi |
| Suppression d'un chantier | Suppression définitive = risque | Action cachée | « J'ai peur d'effacer par erreur » | Pas de suppression dans le parcours courant : **« Marquer terminé »**, réversible. Suppression définitive seulement depuis les réglages, avec confirmation |

## Contrôle technique — constats et corrections

| # | Constat | Gravité | Correction | Preuve |
|---|---|---|---|---|
| T1 | **Double appui** sur « Créer mon entreprise » → 2 entreprises, puis l'artisan est bloqué sur « choisissez une entreprise » | Élevée | En-tête `Idempotency-Key` (table `idempotency_record`, rejeu de la première réponse, clé libérée en cas d'échec, clé propre à chaque utilisateur) sur les créations d'entreprise et de chantier | 5 tests |
| T2 | Envoi trop volumineux → « erreur interne, réessayez » (un nouvel essai échouera toujours) | Moyenne | Code `payload_too_large` (413), non réessayable ; erreurs du parseur de corps traitées | 2 tests |
| T3 | Aucune recherche de chantier | Élevée (usage) | Recherche plein texte sans accents (`unaccent` + `pg_trgm`, index GIN), multi-mots, jokers `%`/`_` neutralisés | 5 tests ; 20 000 chantiers : **1,5 ms** |
| T4 | Tri par création, index sur `updatedAt` inutilisé par la requête | Moyenne | `lastActivityAt` + index `(companyId, status, lastActivityAt DESC, id DESC)` ; migration avec reprise des valeurs (aucune perte) | Test ; 20 000 chantiers : **0,1 ms** |
| T5 | Curseur de pagination non vérifié | Faible | Curseur opaque validé (400 si falsifié) | Test |
| T6 | Expression régulière UUID dupliquée dans deux modules | Faible | `platform/validation/ids.ts` partagé | Lint + tests |
| T7 | Deux appareils modifient le même chantier (téléphone + bureau) : la dernière écriture gagne | Faible aujourd'hui, **élevée** pour la liste de matériaux | Accepté pour les chantiers ; **contrôle de version obligatoire** pour la liste de matériaux (phase 2) | À faire |
| T8 | Pas de limitation de débit sur l'API métier (seulement sur l'authentification) | Moyenne | À ajouter avant l'ouverture publique (phase 5) | À faire |

## Règles imposées à l'application web (à tester en E2E)

1. **Retour = historique réel** du navigateur ou de l'application, jamais
   un lien fixe. Un écran ouvert directement (lien, notification) a un
   « Retour » vers son parent logique (fiche → liste).
2. **Le contexte vit dans l'adresse** : recherche, filtre, onglet et
   élément ouvert sont dans l'URL (`/chantiers?q=dupont&statut=termine`) ;
   Retour les restitue, ainsi que la **position de défilement**.
3. **Rien ne se perd** : brouillons et réponses enregistrés au fil de
   l'eau ; un formulaire quitté par erreur se retrouve tel quel.
4. **Une action = un résultat** : bouton désactivé pendant l'envoi +
   `Idempotency-Key` générée par action.
5. **États** : chaque liste a un état vide qui explique et propose
   l'action utile ; chaque erreur dit ce qui s'est passé, si les données
   sont conservées, quoi faire, et affiche le code support.
6. **Pouce d'abord** : actions principales en bas de l'écran, zones
   tactiles ≥ 44 px, barre de navigation à 5 emplacements maximum.
7. **Ordinateur et tablette** : même organisation. La barre du bas devient
   une colonne à gauche ; la liste et la fiche s'affichent côte à côte ;
   aucune fonction propre à l'ordinateur.
8. **Beaucoup de données** : listes paginées par curseur (défilement
   continu), recherche côté serveur, jamais de chargement « tout d'un coup ».
